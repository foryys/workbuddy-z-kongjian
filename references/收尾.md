# 收尾（每一轮结束）

**先看档位**：

| 档 | 收尾要做什么 |
|---|---|
| **单次** | **不用收尾**——做完直接把东西给用户 |
| **轻长期** | 三件：刷看板 ＋ 按五条判据清退废弃件 ＋ 一句话报告 |
| **长跑** | 四件：上述三件 ＋ git 存档（**没铺 git 的项目跳过存档**） |

**一句话结论：该做的当轮做完 —— 没有「攒着做」了。**

## 1. 核对（轻长期、长跑）

逐条对照 **`看板.html`** 与磁盘上的真实文件：写了"完成"的，产物**真的存在吗**？
不存在就改回真实状态并说明。**不许"补一句话当产物"。**

## 2. 立即做（每轮）

| 更新什么 | 怎么更新 |
|---|---|
| **产物** | 就地改**同一份文件**（一个产物一个文件） |
| **`看板.html`** | **见下方「刷看板的触发点」**——五块：**待办清单**（近期能收尾的，置顶、可折叠）／ **未了清单**（长期挂着的，可折叠）／ 主线 ／ 正在做 ／ 已定事项。**写完不回读全文** |
| **存档** | 长跑档：`git add` **只加本轮动过的文件**（并行期间禁止 `git add -A`）→ 提交。**不 push。**轻长期跳过 |
| **output/ 归类** | `output/` 根上的**散件**（没进任务文件夹的文件）→ 移进**客户端会话名**对应的任务文件夹（半角 `\|` 换全角 `｜`）。查法见 `references/目录纪律.md`「任务文件夹怎么命名」。**只移动，不删** |

### 刷看板的触发点（**2026-09-21 新增：不许攒到"收尾"**）

**病根**：原措辞只说"有变化就改"，**没说"什么时候改"** —— 于是它被归进「收尾」这一档，而**收尾是用户喊的**。结果看板永远比事实慢一步，用户不开口就不更新。

**下面任一条出现 → 当轮立刻刷，不等收尾、不等用户问：**

- **产物状态变了**：完成／新增／作废／版本号变了
- **产生了新决定**（用户拍板的，或双方确认的原则）
- **待办增删**：新冒出来的、办结的、作废的

**只有"这一轮纯过程、上面三样一个没动"时才不刷。**

⚠️ **办结的当场划掉** —— 别留"已经做完还挂在待办里"的条目。用户要看的是"还剩什么"，不是"干过什么"。
⚠️ **两个清单按"短期／长期"分**（2026-09-21 用户拍板）：**待办清单** ＝ 这轮或近期就能收尾的；**未了清单** ＝ 可能挂几周、跨对话的。**两类的优先级不是一回事**，别混装一个块里。
⚠️ **同一件事只在一处说** —— 看板是遗留的唯一出口，**不在对话里另起一份零散清单**（2026-09-21 用户明确要求）。

### git 三查（长跑档且已铺 git；**没铺 git 的直接跳过本节**）

1. **`git status --short` 必须干净**——不干净就逐条看是什么，别直接走人
2. **删过已入库的文件？** —— 同步 `git add -- <路径>` **把删除提交掉**（只从工作区删、不提交 = 工作树永远脏）
3. **动过临时文件？** —— 确认 `.workbuddy/tmp/` 已在 `.gitignore`（没有就补，并一起提交）

> 2026-09-18 实测：`tmp` 清掉后 `git status` 冒出 **663 条**"已删除未提交"——根因是 `.gitignore` 从来没排除过临时目录，933 个过程件早被收进库。

### 目录与体积体检（**跑脚本，不手算**）

```
python "<技能目录>/scripts/体检.py" <项目根>
```

一次出两块报告：**A 目录五项**（一级目录 ≤3／项目根文件 ≤6／`.workbuddy` 顶层 ≤4／顶层散文件 =0／archive 条目数）
＋ **B 体积六项**（项目记忆／用户级记忆／日志／技能 `SKILL.md`／临时区／归档大件）。不合格项脚本标 ⚠️。

**阈值与处置口径只有一个来源**：SKILL **第六节「判定总表」**——本节不重抄数字。
超了**当场归位**（只移动、不销毁）；**删除类操作先出清单让用户点头**。

> ⚠️ **别看错**：项目根**本来就该有几个文件**（`看板.html`／`WORKBUDDY.md`／`.gitignore`／`README`）——
> **要清的是 `.workbuddy` 顶层那些散落的过程文件**。

## 3. 归档检查（每轮收尾顺手做）

**归档检查**：当天的记忆日志达到 SKILL **第六节**的阈值就归档一次——它只增不减，不瘦身会让每轮都变重。

（**复盘那一问不在这里**。）

### 日志归档三件套（2026-09-21 定版｜用户要求「要知道详细日志在哪，但查的时候不要全读」）

当天日志达到阈值时，**先做一次前置检查，再按上表做三件（缺一不可）**：

### ⚠️ 前置检查：这份日志是不是只有你在写？（2026-09-24 补，当天差点踩中）

同一工作空间**可能同时跑多个对话**，它们共用同一份日志与看板。**动原文件前先看 mtime**：

```bash
ls -la --time-style=+%H:%M:%S .workbuddy/memory/YYYY-MM-DD.md
```

- **几分钟内被写过**（且 `git log` 里有不是本对话的提交；**没铺 git 的项目改看 mtime ＋ 旁证文件**）→ **只做「全文存档」，不替换原文件**。替换会把它刚写或正在写的内容冲掉。
- 旁证不止 mtime：`git status` 里出现**本对话没动过的文件**（技能／看板／其他产物）＝ 并行对话在活动。
- 处置：把「**日志超标、未精简、原因＝并行对话**」一句话报给用户，**等他定**（只有他知道有几个对话在跑）。
- **全文存档本身无风险，任何时候都做。**

| # | 做什么 | 规范 |
|---|---|---|
| 1 | **全文存档** | 复制到 `archive/专题-日志归档-YYYYMMDD/memory-YYYY-MM-DD-全文.md`，**一字不改**；**先 `diff` 校验字节一致，再动原文件** |
| 2 | **原文件换精简版** | 抬头**必须写三行**：① 全文在哪（路径 ＋ 字节数）② **怎么查**：「不要整份读，用 Grep 按关键词定位行号，再 Read 前后 20 行」③ 长期结论已升进 `MEMORY.md`；正文只留**当天要点表** ＋ 待续 |
| 3 | **结论升级** | 把**可复用结论**（口径／约定／反复踩的坑）搬进 `.workbuddy/memory/MEMORY.md`——**日志只留流水，结论不留在日志里** |

**为什么这么规定**：日志是累积件，全文存着是为了"查得到"，但**每读一次都吃上下文**。
精简版抬头那三行是**给下一个助手看的**：它一打开就知道「别整份读、去哪查、结论在哪」。
**没有这三行，归档等于埋了**——下次还得靠人回忆"那天到底干了什么"。

### 删除怎么走：**归档 → 分级收口 → 送回收站**

**不许一发现没用就直接删。** 动作三步：

1. **收尾时**把本轮的无用件**移进暂存区** → `archive/待回收-<范围>-YYYYMMDD/`（**只移动，不销毁**）
2. **一句话告诉用户**归档到哪个文件夹 —— 不解释过程
3. **到回收点时**（见下）出清单 → 用户点头 → **送回收站**

**回收点不设单一时点 —— 哪一级收口，就在哪一级清**：

| 层级 | 什么时候 | 清什么 |
|---|---|---|
| **任务级** | 单次任务做完 | 该任务的过程件 → 进暂存区 |
| **支线级** | 一条支线收口（如「第 1 讲课件」完工） | 该支线**全部暂存区 → 送回收站** |
| **项目级** | 整个项目结束 | 所有暂存区 → 送回收站 |

**判据**：**更上一级已完工** → 说明下级的东西不会再动，可以真删。
**为什么不只设「项目结束」**：那个时点可能一年后才到，而助手只在对话里存在 —— **等不到的回收点 ＝ 没有回收点**。

**为什么这么绕**：
- **回收站不是备份** —— 助手**无法可靠地从回收站取回文件**，真丢了只能用户手动还原
- **边做边删 ＝ 每次都在赌**，而"这东西还有用吗"当场最容易判错
- 暂存区把判断**推迟到信息最全的收口**，中途随时捞得回来

### ⚠️ 归档三条硬规则（**改过归档件的人都栽过**）

1. **独立命名，禁止同名覆盖**——归档件一律 `<类型>-<说明>-YYYYMMDD[HHMM].md`。
   实测事故：把新写的日志**同名覆盖**进 `archive/memory-...-全文.md`，新版比旧版小 1.7 KB，**覆盖反而丢内容**（靠 git 捞回）。
   → **确需覆盖的先验「新 ⊇ 旧」**；拿不准就换个带时间戳的新名。
2. **只移动不销毁**——`rm -rf` 禁用；删除类走**回收站**，**先出清单让用户点头**，文件名**逐字核对**（写错一字会被静默跳过），删完**回读目录复核**。
   走回收站的写法见 `references/环境注意.md`（**不能用 `Add-Type`**）。
3. **同一产物的多份快照只留最近 3 份**——不要"每轮一份"（实测 `archive/` 曾堆 7 份同款 38 MB 课件快照 ＝ 258 MB）。
   更早的快照走回收站；**>10 MB 的删除先出清单**。

**例外**：本轮动过**基线文档**（总纲这类）→ 当场确认**看板已刷**。

## 4. 复盘与沉淀 —— **不归本技能**

"这几轮有什么下次还会遇到的坑"、总结经验、优化自定义指令／人设／记忆、维护经验台账，**本技能一概不碰**。
**本技能只管"项目怎么管"。**

**长期有效的提醒项**（用户说"以后每次都要提"）→ 写进项目 `WORKBUDDY.md` 的**「本工作区必提醒」**节，
由「开工」每轮过一遍，**不靠助手记性**。

## 5. 报告（一张分区小表，不是五行文字）

| 栏 | 写什么 |
|---|---|
| **做了** | 一句话结论 |
| **改了** | 改前 → 改后（成对列） |
| **影响** | 影响谁、影响哪几件产物 |
| **遗留** | 还没动的、待用户拍板的 |
| **下一步** | **"这轮该换对话了"**——长跑档一个对话跑满 10 轮即结束，开新对话说「开工」接着做 |

**不复述"我更新了哪几个文件"**。给用户看的东西**优先出 HTML 或表格**，禁止大段文字。

## 禁止

- 不把没做的事写成做完。
- 不自己给自己发合格证（"等验收"→"已完成"只能用户改）。
- 不改验收标准（要先问用户）。
- **不每轮全量刷所有文件**——信息会被淹没，用户也读不出重点。
- **不手写改动明细**（那是 git 的活）。
