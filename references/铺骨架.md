# 铺骨架

空项目铺骨架、已有项目接手、已铺好的项目升级——**三件事共用一套骨架清单**，所以合在一份。

**三条铁律：先看后动 · 铺全不空铺 · 只移动不销毁。**

## 零、进场先定两件事

一次问一个，不要连问。

### 问一：文本型还是代码型

只决定目录个数怎么判（判据见 `判据与阈值.md` 第一节），别的一概不变。

| 回答 | 判法 |
|---|---|
| **文本型**（交付物是文档／表格／PPT） | 项目根一级目录 **≤3**：`archive/`／`output/`／`.workbuddy/` |
| **代码型**（交付物是程序） | 一级目录**不数个数**；`src/` 源码夹与 `bin/` 产物夹各一个，另加那三个；只判根散文件 ≤6 |

答不出来就把判据念给他选：根下有 `go.mod`／`package.json`／`*.sln`／`*.csproj`／`pom.xml`／`requirements.txt`／`Cargo.toml`，或有 `src/`／`bin/`／`dist/`／`app/` 的，是代码型。**别自己猜。**

### 问二：这事做一次还是反复改

| 回答 | 档位 | 铺什么 | 每回合做什么 |
|---|---|---|---|
| 做一次 | **单次**（默认） | **只有 `output/`** | **零仪式**——做完直接给 |
| 会改几轮 | **轻长期** | 加 `看板.html` ＋ 规则副本 | 产物 ＋ 刷看板 |
| 长期迭代 | **长跑** | 加 `WORKBUDDY.md` ＋ git | 再加拍板即落看板、每回合换会话 |

**默认从最低档起步**。用户拿不准先按单次做——他没有记录负担，你也不用维护一堆文件；真需要长期了再加档，**不重做已有内容**。反过来（不问就铺全套）是错的，那正是这个技能最容易被抱怨「繁琐」的地方。

## 一、空项目：怎么铺

先确认是**空文件夹**，别先往里建文件——骨架由模板生成，手建的会跟模板打架。用户说「启动项目：<项目名>」即触发。

**取件对照表**（全部来自本技能目录，不需要配任何路径）：

| 本技能里的 | 铺到项目哪里 | 哪个档 |
|---|---|---|
| `references/project-rules.md` | → `.workbuddy/rules/工作空间规则.md`（复制并改名） | 轻长期、长跑 |
| `assets/看板.html` | → 项目根 `看板.html`（**唯一给用户看的治理文件**） | 轻长期、长跑 |
| `assets/WORKBUDDY.md` | → 项目根 `WORKBUDDY.md` | 长跑 |
| `assets/工作空间规则-本项目.md` | → `.workbuddy/rules/工作空间规则-本项目.md`（**只在「要推翻通用规则」时**给；一般约定写进项目记忆） | 任意 |
| `.gitignore`（手工建，不是模板） | → 项目根，**长跑档且铺 git 的必做** | 长跑 |

**长跑档再问四个**（单次跳过；轻长期只问第 4 问）：① 做成什么，一句话可验收 ② 绝不做什么，至少两条 ③ 验收标准：谁验收、什么叫做完 ④ 第一阶段做什么，并写明本轮不做什么。问完复述给用户确认。**这一步不产出任何业务成品。**

## 二、已有项目：怎么接手

用户说「接手项目，路径：<文件夹>」。

### 2.1 只读盘点

扫目录结构、文件类型、有没有 git、大致规模，出《现状清单》。**这一步一个文件都不动。**

再问三件（一次一个）：还继续做吗（继续／只归档）→ 短期收尾还是长期反复改（定档位）→ 哪些是素材（绝不能动）、哪些是产物（可以继续改）。

### 2.2 铺全，别分批

**接手＝把骨架铺全，不是加个壳就走。** 缺的那几件今天不补，以后每回合都会在同一处卡住。

| 层 | 要有的 | 说明 |
|---|---|---|
| 项目根 | `output/`、`archive/`、`.workbuddy/` | 文本型只这三个；**代码型的 `src/`／`bin/` 原样留着** |
| `.workbuddy/` | `memory/`、`rules/`、`tmp/`、`tools/`、`看板.html` | `memory/` 客户端自带，缺了才建；看板从 `assets/` 取 |
| 规则 | `rules/工作空间规则.md` | 从 `references/project-rules.md` 复制改名；要推翻通用规则的才另建 `工作空间规则-本项目.md` |
| 备忘 | `WORKBUDDY.md` | 从 `assets/` 取，**按盘点结果倒填**，不留空模板 |

已有 git 就**不动历史**，把「接手那一刻」提交一次当锚点。不打 stash、不做 reset。

### 2.3 归位

**接手是唯一一次「可以搬东西」的机会**——过了这村，项目跑起来再搬就是破坏。

- 先出**归位清单**：哪个文件从哪儿到哪儿、为什么。**用户点头才搬。**
- 只搬进已有目录（`output/`／`archive/`／`.workbuddy/tmp/`），**不为装它新建目录**。
- 只移动、不删除、不改名、不重排；归属拿不准的**留在原地**并在清单里标出。
- 搬完复核：根散文件 ≤6、`output/` 顶层无散件、`archive/` 下只有平铺的专题夹。

### 2.4 倒填现状并记录

- 已做完的、在做的（写清在等什么）、接着要做的写清。**看板一建立就是真实状态，不是空壳。**
- **当天写一条日志**：接手了什么、铺了哪几件、搬了什么（从哪到哪）、遗留什么、下一步只做哪一件。**铺骨架和搬家不落盘，下个会话就得从头再盘一遍。**
- 顺手认基线：盘点时指出哪些旧文件是**基线文档**（总纲／需求基线／规范这类，会被反复修订、下游依赖它），给它们补版本号，之后改版走升版三动作。

## 三、已铺好的项目：升级

技能升级过之后，已铺的项目还停在旧框架。用户说「升级项目」才生效，做四件事：

| # | 动什么 | 怎么动 |
|---|---|---|
| 1 | **规则** `.workbuddy/rules/工作空间规则.md` | **整体覆盖**成技能里的最新版。`工作空间规则-本项目.md` **一字不动** |
| 2 | **模板**（看板／WORKBUDDY） | **只补不覆盖**：缺的块按新模板补上，已有内容一行不动 |
| 3 | **删旧章节** | 新模板已取消的章节 → 移进 `archive/<文件名>-旧章节-<日期>.md`，**只移动不销毁**，并在文件抬头注明去处 |
| 4 | **看板** | 用最新模板重新生成——它是视图。**重建前先盘一遍旧看板里模板没有的内容**（项目自己加的区块、手写的话），抄进新看板对应位置，**内容不许丢** |

**第 4 条有一条跳过判据**：先 diff 旧看板与新模板的结构。**结构一致就不整份重建，只改内容**（基线版本、状态、已定事项）——结构没变、没有模板里没有的内容会丢，重建就是搬字。结构确实变了才重建。

**动手前先出清单**：说清改哪几处，用户点头才动。回执五行内：规则 vX → vY ｜ 补了什么、删的几节去哪了 ｜ 看板已重建（或说明了为什么跳过）｜ 原有内容一字未动 ｜ 遗留什么。

不做成自动的理由：自动改用户项目文件的风险，比多问一句大得多。

## 四、铺之前的减件关

往根上加文件**先过三问**，过不了的不给铺：

| # | 问 | 结果 |
|---|---|---|
| 1 | 这条信息除了它还有谁记？ | 有人记了 → **不铺** |
| 2 | 用户会看它吗？ | 不会看 → 放 `.workbuddy/`，不放项目根 |
| 3 | 它是最终交付还是中间件？ | 中间件 → 放 `.workbuddy/`，不进 `output/` |

**一条线只交一件主产物。** 例：做一讲课件，主产物就是那份 `.pptx`；内容大纲、分页结构、制版规格都是中间件。用户要额外交付物时再给，**不主动多产出**。

**骨架那几件不算「文件」，是位置，不参与减件关。**

## 五、git 铺不铺

问一句：**这个项目里「要反复改的文本」占多少？**

- **文本为主**（规则、方案、文档、代码）→ **铺**。价值在版本回溯。
- **设计／大件为主**（PPT、图片、视频）→ **不铺**。这类项目提交的大多是 png／jpeg／pptx，`.git` 白涨，回滚率极低。替代方案：成品按时间戳另存不覆盖（`exports/xxx_123416.pptx`），源件另有 `backup/<时间戳>/` 快照，天然留每一版。
- **没铺 git 的项目**：`.gitignore` 不用建；开工跳过 git 三查；收尾跳过 git 存档。

**铺了就必须先建 `.gitignore`**，至少含：

```
.workbuddy/tmp/
archive/
```

别按扩展名挡——按 `.pptx` 挡只挡住一小部分，剩下 png／jpeg／svg 照样入库。**删掉已入库的文件要同步 `git add -- <路径>` 提交删除**，否则那份「脏」一直挂着。

**产物命名**：一个东西一个文件，改就在里面改。版本号写在**文件里面**（标题旁或页脚），**不写进文件名**；目录也不带版本号（用 `output/第1讲/`，不用 `output/v0.1/`）。旧版靠存档找回。

**顺手定基线**：指一下哪几份算基线文档（会被反复修订、下游有东西依赖它）。**只有它们带版本号**（写在文件里），改版走升版三动作；其余产物不标版本。

## 六、铺完之后每回合怎么说

| 档 | 每回合怎么说 |
|---|---|
| **单次** | **不用说**——直接要东西 |
| **轻长期** | 直接干；想看进度说「开工」，结束说「收尾」 |
| **长跑** | 「开工」→ 干活 → 「收尾」，**收尾就该换会话了** |

**确认铺完的标志**：开一个新会话（或重启客户端），在里面说「开工」——能报出进度，就说明一切都生效了。

## 七、遇到这些情况怎么做

| 情景 | 用户怎么说 | 动作 |
|---|---|---|
| 选了单次，后来要长期改 | 「升成长跑档」 | 补铺骨架（规则副本、看板、`WORKBUDDY.md`、git），不重做已有内容 |
| 想加一步 | 「第 3 步后面加一步：XXX」 | 直接加，看板记一笔原因 |
| 某步做不动 | — | 标 `[!]` 并写清在等什么；用户说「先跳过」就调整 |
| 想改目标或边界 | 「目标改成 XXX」 | 改 `WORKBUDDY.md`，看板记一笔 |
| 只想清几件 | 「清空重做，只留 XXX」 | 出「保留／删除」两份清单 → 逐条点头 → 整目录备份 → 分批走回收站。写法见 `删除与归档.md` |
| 旧项目已有 git | — | 不动历史，只打锚点提交；不 stash、不 reset |
| 旧项目里有别的会话在改 | — | 开工先看 `git status`，有未提交改动就停下问 |
| 迁到一半不想迁了 | 「退回接手前」 | 给一条命令退回锚点，旧文件原样都在 |
| 项目里有自己的规矩 | 「这条规矩只对本项目」 | 一般约定写进项目记忆；**要推翻通用规则**的才写进 `工作空间规则-本项目.md`（那份升级不覆盖） |
| 只是归档、不再做 | 「只归档」 | 只加一个说明文件，**不动任何内容** |
| 旧项目里有没生效的命令文件 | — | 列出来问用户，点头才删 |

**说「开工」即进入 `开工与收尾.md` 的流程。**
