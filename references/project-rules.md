# 工作空间规则

> 来自「工作空间优化」技能 **0.10.0** ｜ 项目里**唯一**的规则来源，**开工时读「〇、开工必读」**。
> 项目里那句 `.workbuddy/rules/工作空间规则.md` 是从「工作空间优化」技能里 `references/project-rules.md` 复制来的**副本**；
> 要改规则，改技能里那份，再同步到各项目——**不要在项目里单独改**。

---

## 〇、开工必读（**只读这一段**；细则用到哪章再读哪章）

> **为什么单列这一节**：整份读会让每一回合都变慢。**每回合只读这 20 行**就够了，其余章节按需再翻。

**先记住目的**：这套东西**只为让多回合项目不失控**——进度看得见、决定可追溯、换个对话接得上。
**它不追求"记录完整"。** 任何动作只要 ① 让任务变慢、② 让用户多读东西、③ 与别处重复——**砍掉**。

**先定多重**：**默认最轻**。开项目先只建 `output/`；要加文件先过"减件关"（第二章）。
**一条线只交一件主产物**，中间件放 `.workbuddy/`，不进 `output/`。

**每回合立即两件**：产物（就地改同一份）／**看板**（**只在有决定或待办变化时改**）。
**归档检查**：并入每回合收尾（不再攒）。
**当场就记**：用户拍板过的决定、基线升版。

**读入有预算**（长跑档单回合合计 **≤ 20 KB**）：规则只读本节；记忆只读 `MEMORY.md`（**日志不读**）；
`changelog.md`／素材登记**不读**；**看板只读「主线」与「要做的事」两块**。

**给用户看的**：一屏看完、能用表就用表、变更成对列、**不复述"我更新了哪几个文件"**。

**少调用（治卡顿，第一优先级）**：一次只走一条路；读过的文件不重复读；写完不回读全文；
合并写盘；不复述文件内容——**转录里 77% 是工具调用，多一次调用就多两条记录**。
**换会话**：一个会话跑满 **10 回合**、转录超 **20 MB／5000 条**、或用户说「收尾」→ 结束后**开新会话**接着做。

## 一、四条底线

1. **写下来才算数**——聊过的决定不落进文件，等于没发生。
2. **一条信息只落一处**——同一件事两处维护，早晚打架（见第三章职责矩阵）。
3. **不拖慢任务**（元规则）——新增文件／章节／动作前先自问"不加行不行"，**不加是默认**；
   加一条之前，先看能不能合并或替换掉一条。规则只增不减就是繁琐。
4. **说三遍就固化**——重复的要求做成规则，重复的错误做成检查。

## 二、先看这件事有多重（默认最轻）

| 档位 | 什么时候 | 铺什么 | 每回合动作 |
|---|---|---|---|
| **单次**（默认） | 做一次就完（一份课件、一次调研） | **只有 `output/`** | **零仪式**——直接做，做完给用户看 |
| **轻长期** | 会改几回 | ＋`看板.html` ＋规则副本 | 产物 ＋ 看板 |
| **长跑** | 长期迭代（像课程体系） | ＋`WORKBUDDY.md` ＋git（**要不要 git 看"要反复改的文本占多少"——设计／大件为主的项目不铺**；记忆走原生 `.workbuddy/memory/`，**不用铺**） | 上表 ＋ git 存档（没铺则跳过）＋ 每回合换会话 |

**默认从最低档起步，用户说要长期才往上加。反过来（不问就铺全套）是错的。**

### 减件关（铺任何文件之前必过）

| # | 问自己 | 答不上来怎么办 |
|---|---|---|
| 1 | **这条信息除了它还有谁记？** | 已经有人记 → **不铺**（例：项目记忆若已记进展，就不必再铺一份"进展"文件） |
| 2 | **用户会看它吗？** | 不会看 → 放 `.workbuddy/`，**不放项目根目录** |
| 3 | **这份东西是最终交付，还是中间件？** | 中间件（内容大纲、分页结构、规格、草稿）→ 放 `.workbuddy/` |

**一条线只交一件主产物。** 要额外交付物，由用户点名，不主动多产出。

## 三、一份信息只落一处（职责矩阵）

| 文件 | **唯一职责** | **不写什么** | 字数上限 |
|---|---|---|---|
| 记忆 `MEMORY.md` | 长期约定 ＋ 反复踩的坑 | 进展、当前状态、改了哪些文件 | — |
| 记忆日志 | **只记坑与决定** | 逐回合过程叙述、逐文件同步面清单 | 单条 ≤ 5 行 |
| 技能 `references/changelog.md` | **技能自己**的版本史（改了什么、为什么） | **项目记忆与日志不抄** —— 要查去技能里查 | — |
| `看板.html` | **唯一给用户看的界面**：待办清单 ／ 未了清单 ／ 正在做 ／ 已定事项 | 逐条改动、改版记录、文件清单、过程叙述 | 一屏 |
| git 提交 | **什么时候改的、改了什么** | — | 一行 |

**三条推论**

1. **"什么时候改的"由 git 回答**——所以**不手写改动表**（这是取消进度「改动」表、账本「变更」表的原因）。
2. **"为什么"只在决策里写一次**；常规改动没有"为什么"可写。
3. **同一件事写第二遍就是错**——发现重复就删掉一处，不要"两处都留着以防万一"（**日志抄 changelog 就是典型**）。

## 四、每回合动作

### 立即做（每回合）

| 动作 | 单次 | 轻长期 | 长跑 |
|---|---|---|---|
| 产物落盘（`output/`） | ✅ | ✅ | ✅ |
| 更新 `看板.html`（**只在有决定或待办变化时改**） | — | ✅ | ✅ |
| 用户拍板即落看板「已定事项」 | — | — | ✅ |
| 存档（git，一句话带过） | — | — | ✅ |

### 不会再有「攒着做」

归档检查**并入每回合收尾**（超阈值就瘦身，见第十章）；复盘与经验沉淀**不归本技能管**。

> **该当场记的不能拖**：用户拍板过的决定、基线升版，当场就记——拖了会失真。

**开工**（长跑档）——读完文件回三行，**等确认再动手**：

```
做到哪  第 2 阶段 ｜ 第 1 讲已定稿 ｜ 正在做：…
待办  等您回传素材
风险  演示页视频会随页序移动，重导后需重插
```

**干活**——做完一件立刻落盘，说一句"改了哪、结果如何"。不攒着一起报，**不复述文件清单**。

**收尾**——回一张**分区小表**（做了／改了／影响／遗留），并提一句 **"这回合该换会话了"**。

## 五、"做到哪"怎么写（写进看板「正在做」块）

六个标记，只用这六个：

| 标记 | 含义 |
|---|---|
| `[ ]` | 没开始 |
| `[~]` | 正在做 |
| `[?]` | 做完了，等用户验收 |
| `[x]` | 已验收通过 |
| `[!]` | 卡住了（**必须写清"在等什么"**） |
| `[-]` | 取消（留在原位，不要删） |

写法——**一条步骤最多两行**：

```
- [~] S05 · 生成第 1 讲课件 → `output/第1讲/第1讲课件.pptx`
  验收：27 页齐备、演示用实采素材 ｜ 依赖：S04
```

1. **每步必须有产物文件**，路径写在步骤行里；没有产物的叫"讨论"，不算步骤。
2. **编号只增不重排**：删掉的标 `[-]` 留原位；拆分写成 `S04a / S04b`。
3. **只有用户能把 `[?]` 改成 `[x]`**，助手不能自己发合格证。
4. **已收口的事超过 3 行就压成 1 行**；明细进 git 与归档，**不留在看板里**。
5. **一个产物一个文件**：就地改，**不新出 v2／v3**；版本写在文件里面（标题旁或页脚），不写进文件名；
   目录也不带版本号。旧版靠存档找回。

## 六、看板怎么写（`看板.html`）

- **它是唯一给用户看的界面**，也是"当前状态"的唯一落点。
- **只在有决定产生或待办有变化时改** —— 不跟进度走、不每回合刷。
- **三块**（下表顺序＝看板从上到下；**2026-10-13 定版**）：

| 块 | 内容 |
|---|---|
| **主线**（置顶） | 推进流程，**画成"连体色带"**（3×2 六格等宽、两端贴齐；浅绿＝已完成／实绿＝在做／灰＝还没到），下面一行小字写"现在到哪" |
| **要做的事** | **三组合一**：`正在做 → 近期能收尾 → 长期挂着`；**同一件事只写一处**（分三块时最容易重复）；没有**不删块**，写「暂无待办 —— 一切尽在掌握」 |
| **已定事项** | 只放**仍生效**的决定；旧条目攒到 **10 条以上**就清退一批 |

- ⛔ **不做「产物入口／打开文件夹」栏位**。预览面板拦截一切非 http／https 导航，页面侧没有打开路径的接口；`file://` 链接、`target="_blank"`、`window.open()`、`location.href` 全失败。要看文件夹只能本地双击 .html，或让用户复制路径。
- **内容分离用多视图**：**同一文件内**分视图（总览／总纲／各讲）；**不拆成多个文件**（项目根文件数 ≤6）。视图按需增加，不预铺空的。
- **怎么切换**：**没有顶部导航栏** —— 从总览的「分视图入口」卡片进，子视图顶部「‹ 总览」返回；**点击由脚本接管（入口须带 `data-go`）**，「靠页面改地址跳转」在预览里会被拦。
- **面向手机**：卡片风、字号偏大；动效**纯 CSS**（切视图自动重播），**零依赖 ＋ 3 秒兜底**（不许引 CDN —— 断网要能看）。模板见 `assets/看板.html`。
- **不进看板的**：逐条改版记录、最近改动、每次改动明细、文件清单。
- 顶部一行：项目名 ｜ 一句话方向 ｜ 当前基线 ｜ 刚更新 `09-16 15:47`（短日期，不写年份）。

## 七、步骤要变 / 做坏了怎么退

| 动作 | 谁决定 |
|---|---|
| 加 / 删 / 拆 / 合并 / 调顺序 | 助手直接改，看板里记一行原因 |
| **改验收标准** | **必须先问用户** |

**做坏了**：撤那一次提交（历史保留）；整批作废就回到本回合开头的版本，**坏版本留着不删**；
大改或试新方案另开分支，成了再合并。**同一处改到第 3 次还不顺 → 停手**，回来看目标是不是定错了。

**推倒重来**：优先"换新空间"（新目录只拷要留的）→ 其次"原地封存"（移进 `_legacy/`）→ 直删最后考虑。
真要删：出「保留／删除」两份清单 → 用户逐条点头 → **整目录备份** → 分批（每批 ≤10）**走回收站**，
禁用 `rm -rf` → 看板记一笔。**三样删了拿不回**：素材（输入源）、项目记忆、提交历史。

## 八、多个对话同时干活

1. **动手前先认领**：该步标 `[~]`，行末加 `｜ 认领：@对话名 时间`。
2. **开工先看 `git status`**：有别人没提交的改动 → **停手问用户**。
3. **收尾必须提交**，且不许覆盖别人的改动。
4. **另一条线在跑时**：自己的记忆与素材登记**只做末尾追加**，不覆盖对方段落。

## 九、文字纪律 ＋ 交付前自检

1. **正文里不写编号，直接写名字**（✗"与 W20 呼应" → ✓"与「权限与安全沙箱」呼应"）。
2. **一份文件最多一套编号体系**；编号只用于在表格里定位。
3. **能用表就不写段落**；一行能说完的不写三行；术语第一次出现附一句解释。
4. **每个入口的动作不超过 3 步**；超了就是设计有问题。
5. 给用户看的：**一屏看完**、**变更成对列**、**默认出 HTML**、**不复述"我更新了哪几个文件"**。

### 交付前自检三条（放之四海而皆准）

**用户视图文件 ＝ `output/**` 与 `看板.html`。** 出现任一条即判不合格，改完再交：

| # | 检查 | 判不合格的样子 |
|---|---|---|
| 1 | **有没有内部编号** | 出现 S03a／D-45／B09 这类编号 |
| 2 | **有没有过程痕迹** | 修订记录、改动次数、"第 N 次改版"、被否方案 |
| 3 | **是不是超过一屏** | 用户要滚动才能看完 ＝ 减法还没做完 |

## 十、上下文纪律与卡顿防治（**第一优先级**）

> **换会话的轮转线**：单会话转录 **>20 MB** 或 **>5000 条**、或一个会话跑满 **10 回合** → 立刻收尾、开新会话接着做；同时开着的会话窗口 **>2 个** → 关掉不用的（每个活跃会话占一个常驻进程）。**卡了就重启客户端**（回收 WAL、清内存）。
> 本节的「少调用／读入预算／归档／删除流程」是**每回合要用的硬规则**，留在本文件。

### 少调用（硬规则）

1. **一次只走一条路**——用户说什么就做那一件，**不顺便把看板／记忆／规则全刷一遍**。
2. **同一动作不重复**：读过的文件不重复读；写完的文件**不整份回读**（只核验关键字段）。
3. **能一次取回的不分两次**：一次 `Read`、或一次 Python 扫，取回所有需要的段。
4. **合并写盘**：同一回合的多处改动攒到**一次写完**，不要改一处写一次。
5. **不复述**：回复里不重贴文件内容、不列"我改了哪几个文件"——**复述本身也会进转录**。

### 读入预算（长跑档单回合合计 **≤ 20 KB**）

| 文件 | 怎么读 |
|---|---|
| 本规则 | **只读「〇、开工必读」** |
| 记忆 | 只读 `MEMORY.md`；**日志不读** |
| `changelog.md`／素材登记 | **不读**（要用时用 grep 定位） |
| `看板.html` | 只读「主线」与「要做的事」两块 |

### 归档（超阈值就瘦身）

| 文件 | 何时归档 | 怎么归档 |
|---|---|---|
| 记忆日志 | 单份超 **8 KB** | 可复用结论升进 `MEMORY.md`，过程移入归档 |
| `看板.html` | 不设阈值 | 「已定事项」攒到 **10 条以上**就清退一批旧条目 |

**三条不许**：**不许删**（只移动）／**不许改**（搬运时一字不动）／**不许把归档当垃圾**（抬头写清位置）。

**谁做**：每回合收尾顺带检查；或用户说「**瘦身**」时立刻做。**动手前先出清单**。

### 删除怎么走：**归档 → 分级收口 → 送回收站**

**不许一发现没用就直接删。** 动作三步：

1. **收尾时**把本回合的无用件**移进暂存区** → `archive/待回收-<范围>-YYYYMMDD/`（**只移动，不销毁**）
2. **一句话告诉用户**归档到哪个文件夹 —— 不解释过程
3. **到回收点时**（见下）出清单 → 用户点头 → **送回收站**

**回收点不设单一时点 —— 哪一级收口，就在哪一级清**：

| 层级 | 什么时候 | 清什么 |
|---|---|---|
| **任务级** | 单次任务做完 | 该任务的过程件 → 进暂存区 |
| **支线级** | 一条支线收口（如「第 1 讲课件」完工） | 该支线**全部暂存区 → 送回收站** |
| **项目级** | 整个项目结束 | 所有暂存区 → 送回收站 |

**判据**：更上一级已完工 → 下级的东西不会再动，可以真删。**只设「项目结束」不行**：那个时点可能一年后才到，而助手只在会话里存在——等不到的回收点等于没有回收点。

**两条前提**：回收站不是备份，取回只能靠用户手动还原；边做边删是在赌「这东西还有用吗」，当场最容易判错——暂存区把判断推迟到信息最全的收口，中途随时捞得回来。

### 项目里「要读的文件」与上限

| 文件 | 管什么 | 怎么读 | 上限 |
|---|---|---|---|
| `WORKBUDDY.md` | 项目目标 · 验收 · 口径 · 当前阶段 | **开工整份读** | **6 KB ／ 60 行** |
| `.workbuddy/rules/工作空间规则.md` | 怎么管工作空间 | 开工**只读「〇、开工必读」** | **24 KB**（必读段 **2 KB**） |
| `.workbuddy/rules/PPT改页技术笔记.md` 之类 | 专业手册（改 PPT 的配方） | **按需查对应章**，不整份读 | **24 KB** |

**为什么分开定上限**：读法不同（整份读／只读一节／按需查章）。超了按工序拆成独立文件。**抬头必须写清读法**。

### 目录纪律（硬上限；**建目录前先问**）

**为什么**：项目做大时**目录比文件更容易失控**，而且多半挤在 `.workbuddy` 里。

| 层 | 上限 |
|---|---|
| **项目根** | **文本型**：一级目录 **≤ 3**（`archive/`／`output/`／`.workbuddy/`）；**代码型**：不数目录个数，`src/`／`bin/`／`dist/` 各留一个、不另起同类，另加同样那三个。两型都：文件 **≤ 6**，根下只准视图与入口（`看板.html`／`WORKBUDDY.md`／`README`），**不落过程文件** |
| **`.workbuddy/`** | **固定 4**（`memory/` `rules/` `tmp/` `tools/`）—— `tmp/` ＝ 用完即弃（收尾后 0 件）；`tools/` ＝ 长期脚本与工具工作区。**不再有内部 `archive/`、不再放专题目录** |
| **`archive/`** | **只在项目根**，只准**平铺**：`专题-<主题>-YYYYMMDD/`（＋ 暂存区 `待回收-<范围>-YYYYMMDD/`） |

**三条动作纪律**：① **建新目录前先问用户**——默认答案是"挂到已有目录下"（专题过程件 → `archive/专题-XXX-日期/`，本回合脚本与当期过程件 → `tmp/`）
② **不按回合／按页／按版本建目录**，`P09/`、`round2/`、`v3/` 这类临时分组不许出现在顶层
③ 工具自建的工作区（`ppt-master` 这类）放 `.workbuddy/tools/` 下，**每个项目只留当前一份**。
④ **`output/` 的任务文件夹名 ＝ 客户端会话名**：不另起简称；会话名带半角 `|` 的用**全角 `｜`** 替（半角在 Windows 文件名里非法）。查法：`~/.workbuddy/workbuddy.db` 的 `sessions` 表，按 `cwd LIKE '%<项目名>%'` 过滤，`custom_title` 优先、`title` 兜底。**只读打开**（`mode=ro`），不直连改。

**收尾做目录体检**：`一级目录数（仅文本型判 ≤3）／项目根文件数（≤6）／.workbuddy 顶层数（≤4）／.workbuddy 顶层散文件数（=0）／archive 顶层条目数`。
代码型由脚本自动认（`go.mod`／`package.json`／`src/`／`bin/`），或 `--type code` 指定。
⚠️ 别看错——项目根**本来就该有几个文件**（看板与入口），**要清的是 `.workbuddy` 顶层散落的过程文件**。

**`.gitignore` 必须含** `.workbuddy/tmp/`——漏了会让临时件**正常入库**
（实测 933 件进了 git、`.git` 涨到 **515 MB**；清掉后 `git status` 还会挂 600 多条"已删除未提交"）。
**归档目录整目录排除**（别按扩展名挡——实测按 `.pptx` 只挡住 19 个，剩下 png/jpeg/svg 近 2000 个照样入库）：写 `archive/`。
删掉已入库的文件要**同步提交删除**。**没铺 git 的项目跳过本节。**

## 十一、基线升版（总纲这类文件改版怎么办）

| 类型 | 是什么 | 例子 |
|---|---|---|
| **基线文档** | 会被反复修订，而且下游有东西依赖它 | 总纲、需求基线、规范 |
| **下游产物** | 依据基线做出来的东西 | 每一讲的课件 |

**基线文档必须带版本号**（`v1` `v2`…），写在**文件里面**，就地改、**不另存新文件**；**改前先 git 存一次**。

**升版两动作**（少一个都算没做）：① 就地改，**版本号 +1** ② **刷新看板**
——顶部基线行与「已定事项」同步（时间到分钟、新版本、波及谁）。

**一条硬规矩**：**先升基线，再产出下游。** **不给普通产物强制标版本**。

## 十二、什么时候该沉淀 / 规则自己也要改

- 同一类错误犯到**第 2 次** → 写进本文件，或做成检查脚本。
- 做过一次取舍 → 落进**看板「已定事项」**，**连被否掉的方案和理由一起记**。
- **"助手怎么进步"不归本文件** —— 总结经验、改自定义指令／人设／记忆，**本文件一概不写**。
- **本文件带版本号**（见文首）。每次被现实打脸，就改一条，并记进技能的 `changelog.md`。
- **读记录先解指代再引用**：见到「本项目」「上次」「之前那份」这类**相对词**，先确认它指谁，**不许拿当前环境硬套**（2026-09-21 把 changelog 里「本项目」误认成当时所在项目）。
- **状态类信息一律现读权威源**：技能当前版本**只认 `SKILL.md` 文首**；`changelog.md` 是历史，**不能拿它反推"现在第几版"**。动手前现读一次，不凭记忆。

## 十三、接手一个已经有东西的项目

五步，顺序不能变。**先看后动 · 铺全不空铺 · 只移动不销毁。**

**0 问型**（只定目录个数怎么判，见十节）→ **1 只读盘点**（出《现状清单》，一个文件都不动）→
**2 问三件**（还做吗／短期还是长期／哪些是素材、哪些是产物）→ **3 铺全骨架**（`output/`／`archive/`／`.workbuddy/` 四件
＋ 看板＋规则副本＋`WORKBUDDY.md`，**一次铺齐、不留空模板**；`git init` 后提交"接手那一刻"当锚点）→ **4 归位**（**允许搬**，
先出清单、用户点头才搬；只搬进已有目录，不删不改名不重排，拿不准留原地）→
**5 倒填 ＋ 记录**（看板写清做完／在做（等什么）／接着做；**当天写日志**：铺了什么、搬了什么、遗留什么、下一步一件）。

已有 git 的项目**不动历史**，不打 `stash`、不做 `reset`；有未提交改动先停下问用户。
命名约定只约束新产生的文件；旧文件不删——要归档就移进 `_legacy/`，保留原路径。

## 十四、项目自己的规矩 & 技能↔项目怎么互相更新

- 通用规则在本文件，**从技能的 `project-rules.md` 复制、平时不动**。
- **"项目自己的规矩"分两类放，不要混在一起**：
  - **一般的项目约定**（口径、验收标准、素材怎么管、产物写法…）→ 写进**项目记忆**
    `.workbuddy/memory/MEMORY.md`。它由客户端自带、**开工就读**，是项目约定的默认落点。
  - **要推翻本文件里某条通用规则**（"这条在本项目不适用／反着来"）→ 才建
    `.workbuddy/rules/工作空间规则-本项目.md`（**真有需要才建**），抬头写死 **"与本文件冲突时，以本文件为准"**。


- **为什么要分**：`.workbuddy/rules/` 下那份若不设门槛，就会和项目记忆**两个载体干同一件事** —— 同一批约定放两处，早晚打架。
- 技能升级时**只替换 `工作空间规则.md`**，`工作空间规则-本项目.md` 一字不动 → 定制永不丢。
- 同一条定制在第二个项目又出现 → 说明它不是项目专属，**升为通用规则**，并把项目里那条删掉。

### 技能 → 项目：用户说一句「升级项目」

技能升级后，已经铺好的项目**不会自动拿到**。做四件事：

| # | 动作 | 硬要求 |
|---|---|---|
| 1 | **换规则** | 技能里的规则**整体覆盖** `.workbuddy/rules/工作空间规则.md`；`工作空间规则-本项目.md` 一字不动 |
| 2 | **补模板** | 只补不覆盖：缺的列与块按新模板补上，已有内容一行不动；新增列**留空** |
| 3 | **清退废弃载体** | 新规则已取消的文件（如 `进度.md`／`账本.md`）按**五条判据**处理，删除**先出清单、用户点头、走回收站** |
| 4 | **重建看板** | 按新模板重新生成；**先盘一遍旧看板里"模板没有的内容"**（项目自己加的区块、手写的一段话），抄进新看板——**视图可重建，内容不能丢** |

**动手前先出清单**，用户点头才动。**回执五行内**：规则 vX → vY ｜ 补了什么、删了什么去哪了 ｜ 看板已重建 ｜ 原有内容一字未动 ｜ 遗留什么。

### 项目 → 通用：经验往哪去

**"这几回合有没有下次还会遇到的坑"这类复盘与沉淀，不归本技能管**。
项目自己的规矩按**第十四节**分两类放：一般约定进**项目记忆**；只有"要推翻通用规则"的才进 `.workbuddy/rules/工作空间规则-本项目.md`。
本技能自身要改时：**只有用户点头才改**；改完 **技能版本 +1** ＋ `changelog.md` 记一行，
并提醒**已铺好的项目说一句「升级项目」**才跟上。
**该升的判据**（三档）：**行为／内容／模板变了 → 升**（哪怕只改一个口径）；**纯排版压缩、错别字 → 不升**；
**追平类 → 也不升**——实现早已改过、也升过版，只是**当时漏改的说明文字**事后补上，属**同版次内补记**。

> 一句话记法：**先问「实现变了没」**——实现变了就升；**实现没变、只是文档没跟上**就补记。
