# 已有项目：接手与升级

> **规则和模板都在本技能目录里**：`references/project-rules.md` ＋ `assets/`。
> **不需要配任何路径。**

适用：**已经在做的项目**、**散落的一堆资料**、**想清空重做的项目**。

**三条铁律：只加不改 · 不搬家 · 先看后动。**

## 第 1 步 · 让用户告诉我项目在哪

用户说一句：**「接手项目，路径：<文件夹>」**

## 第 2 步 · 出《现状清单》，回答三件事

先**只读扫描**：目录结构、文件类型、有没有 git、大致规模。
**这一步一个文件都不动**——只读、只报告。

然后一次问一个：

1. **这项目还继续做吗？**（继续 / 只是归档）
2. **短期收尾还是长期反复改？**（定档位）
3. **哪些是素材**（绝不能动）、**哪些是产物**（可以继续改）？

## 第 3 步 · 加壳不改件 → 倒填现状 → 正常开工

- **先过「减件关」**（规则第二章）：这条信息除了它还有谁记？用户会看它吗？是交付还是中间件？
  **过不了关的文件不给铺**——接手一个乱项目时最容易顺手铺一堆，那正是"越用越繁琐"的来源。
- 只在根目录**新增过完关的那几个**文件（＋ 看板，从本技能 `assets/` 取）；
  **默认只铺 `看板.html` ＋ 规则副本**；长跑档再加 `WORKBUDDY.md`，
  **当场问用户要不要**——不替他决定。
  （**原生记忆 `.workbuddy/memory/` 是客户端自带机制，不用铺、不用问**，日志与长期笔记按需直接写。）
  已有 git 就**不动历史**，把"接手那一刻"提交一次当锚点。
- **既有文件一个不挪、不改名、不重构目录。**
- 把已经做完的标 `[x]`、在做的标 `[~]`、接着做的标 `[ ]`——
  **看板一建立就是真实状态，不是空壳。**
- **顺手认基线**：盘点时指出哪些旧文件是**基线文档**（总纲 / 需求基线 / 规范这类，
  会被反复修订、下游依赖它）→ 给它们补上版本号，之后改版走「升版三动作」。

之后跟新项目一样：说「**开工**」→ 干活 → 说「**收尾**」。

## 已经接入的项目，怎么升级（触发词：升级项目 / 项目升级 / 同步规则）

技能升级过之后，**已经铺好的项目还停在旧框架**。用户说一句就能跟上，做**四件事**：

| # | 要动的 | 怎么动 |
|---|---|---|
| 1 | **规则**（`.workbuddy/rules/工作空间规则.md`） | **整体覆盖**成技能里的最新版；`工作空间规则-本项目.md` **一字不动** |
| 2 | **模板**（看板 / WORKBUDDY） | **只补不覆盖**：缺的块按新模板补上，已有内容一行不动 |
| 3 | **删旧章节** | 新模板已取消的章节——v0.6.0 起是：进度「改动」表、账本「变更」表与「每轮小结」；**v0.9.0 起：`进度.md`／`账本.md` 两个模板整体取消**——**移进 `.workbuddy/archive/<文件名>-旧章节-<日期>.md`**（只移动、不销毁），并在文件抬头注明去处 |
| 4 | **看板**（`看板.html`） | **用最新模板重新生成**——它是视图；**但重建前先盘一遍旧看板里"模板没有的内容"**（项目自己加的区块、手写的一段话），抄进新看板对应位置，**内容不许丢** |

**第 3 条要特别讲清"为什么删"**：这些表与"什么时候改的"这件事重复了——那件事由 git 提交回答。
删的是**重复记录**，不是历史：原文完整躺在归档里，要查随时查得到。
**删之前必须让用户看到清单**：删哪几节、移到哪个文件、抬头写什么。

**动手前先出清单**：说清要改哪几处，用户点头才动。
**回执**（五行内）：规则 vX → vY ｜ 补了什么、删的几节去哪了 ｜ 看板已重建 ｜ 原有内容一字未动 ｜ 遗留什么。

**为什么不做成自动**：自动改用户项目文件的风险，比"多问一句"大得多。

## 遇到这些情况怎么做

| 情景 | 用户怎么说 | 会发生什么 |
|---|---|---|
| 只想要一部分，其余清掉 | 「清空重做，只留 XXX」 | 先出「保留 / 删除」两份清单 → 用户逐条点头 → **整目录备份** → 分批走回收站，禁用 `rm -rf` |
| 旧项目里已有 git | — | **不动历史**，只打一个锚点提交；不打 `stash`、不做 `reset` |
| 旧项目里有别的对话在改 | — | 开工先看 `git status`，有未提交改动就停下问用户 |
| 迁到一半不想迁了 | 「退回接手前」 | 给一条命令退回锚点，旧文件原样都在 |
| 项目里有自己的规矩 | 「这条规矩只对本项目」 | **一般约定**写进**项目记忆**；**要推翻通用规则的**才写进 `.workbuddy/rules/工作空间规则-本项目.md`（那份规则升级不会覆盖） |
| 不想迁移，想开个全新的 | 「开新的」 | 转「新项目」那一节，新文件夹从零来 |
| 只是归档、不再做 | 「只归档」 | 只加一个说明文件，**不动任何内容** |
| 旧项目里有没生效的命令文件 | — | 列出来问用户，**点头才删** |

## Windows：怎么真正「走回收站」（2026-09-14 实测；2026-09-20 补第 4~6 条；2026-10-13 补第 7 条）

`rm -rf` 是真删，**禁用**。Windows 上把文件/目录送进回收站，**唯一实测可行**的写法是 PowerShell 直接引用 .NET 类型：

```powershell
# 删文件
[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteFile('C:\path\a.md','OnlyErrorDialogs','SendToRecycleBin')

# 删目录（含全部内容）
[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteDirectory('C:\path\dir','OnlyErrorDialogs','SendToRecycleBin')
```

**六条实测教训**

1. `Add-Type -AssemblyName Microsoft.VisualBasic` **会被本机安全策略拦下**（提示 "Add-Type compiles and loads .NET code at runtime"）——但该类型**无需 Add-Type 即可直接引用**，别画蛇添足。
2. **别走 ctypes 直调 `SHFileOperationW`**：结构体传参有坑，实测返回 `rc=2`（文件未找到），此路不通，却最容易被当成"首先想到的方案"。
3. **删目录后会残留空目录壳**（本例 `.git/refs/tags` 残留两层）——需再补 `rmdir`（只删空目录，安全）。删 `.git` 这类深层目录尤其明显：`DeleteDirectory` 清掉内容后，壳还在，且 `attrib` 显示带隐藏属性。
4. **`try/catch` 会全命中，却不代表删除失败**（2026-09-20 复现）：反射取类型后循环删 26 个文件，`catch` 里逐条记下 `FAIL`，实际**全部成功进了回收站**（源目录归零、回收站里 `$I`/`$R` 成对出现）。
   → **判成败只看结果，不看 catch**：① 源目录文件计数归零；② 回收站里确有成对条目。
   → 反向同样要警惕：**`catch` 没报错也不等于删成功**，照样得回读目录。
5. **删目录会「假报错」，且不止一种文案**（2026-09-20 **两次**实测）：`DeleteDirectory(…, SendToRecycleBin)` 会抛
   「**这个系统不支持该功能**」或「**系统调用级别不正确**」，但**内容其实已经进了回收站**。
   → 两次实证：① 删 402 文件／28 子目录 → 回收站记 **421 条**，全在该目录下，**目标目录已消失**；
   ② 删 158 文件／8 子目录（21.51 MB）→ 回收站记 **153 条**、**字节合计 22.87 MB ≥ 删除前**，**调用后目标目录仍在**（只剩空壳）。
   → **判成败只看结果**（同第 4 条），做**三个核对**：① 源路径是否已空／不存在；② 回收站里按原始路径查得到；③ **按字节量对账**（回收 ≥ 删除前 即无丢失）。**别被报错骗回去重做。**
   → 调用后**目录还在，多为只剩空壳**——再走一次回收站或删空壳即可，别当"没删掉"。
6. ⛔ **回收站调用后面，绝不要写 `Remove-Item -Recurse`（或 `rm -rf`）兜底**（2026-09-20 自查发现）：本想"报错就硬删保底"，实际是**一旦真没进站，就把它硬删了**——等于绕过回收站。
   **兜底只允许 `rmdir`（仅删空目录）**；要清残留就**再走一次回收站调用**。
7. ⚠️ **回收站超上限后，新删文件不进站、直接永久删除**（2026-10-13 复核出的根因）：本机曾堆到 **19.2 GB**，当天所有删除都"看着失败"，并因此被误判成"通道被策略拦死"。**用前先确认回收站没满**；判据照旧：**源路径消失 ＋ 回收站按原始路径查得到**，两条都满足才算进站。

**验证要另想办法**：本机 PowerShell 工具**不回显 `Write-Output` 输出**，删除是否成功须用 Bash 侧的 `ls`/`find` 复核，不能靠脚本自己打印。

## Windows：bash 的坑（2026-09-16 复测更新）

- **Bash 的 PATH 可能整体是坏的**：`ls`／`dirname`／`head`／`grep` 一律 `command not found`（shim 找不到 dirname），
  **连 `ls -la` 都跑不了**。两条路：
  1. 命令前导出 PortableGit 路径（**真实路径按本机实际版本号取**）：
     `export PATH="/c/Users/<用户>/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:/c/Users/<用户>/.workbuddy/binaries/PortableGit/versions/1.2.0/mingw64/bin:$PATH"`
  2. **干脆不走 Bash**：列文件与统计体积用 **Glob（带 `path` 参数）**，读内容用 `Read` / `Grep`。
     **这条更省事，先试它。**
- **PowerShell 工具可能完全不回显 stdout**：连 `"HELLO"; Get-Location` 都返回空（退出码却是 0）。
  **别拿"退出码 0"当执行成功的证据**——用 `Read` / `Glob` 回读确认结果，或改走 Bash 侧复核。
- 往 `%TEMP%` 落盘会**静默失败**（`mkdir` 不报错，但随后写文件报 "No such file or directory"）。要临时处理数据就用 Python 在内存里做完，**别落盘**。
- Windows 版 curl 的 `-o /dev/null` 会以 `rc=23` 结束（写不进去），但 **HTTP 状态码仍然可信**；要统计响应字节数得改用 Python。
