# 开工与收尾

## 零、三个词先分清

混用会让流程判断出错，读这份文件前先对齐：

| 词 | 指什么 | 判断依据 |
|---|---|---|
| **会话** | 客户端里一个对话窗口 | 换窗口就是换会话 |
| **回合** | 会话内一次用户发话＋助手应答 | 每来一条消息算一回合 |
| **阶段** | 项目推进的一段（可跨多个会话） | 看板主线上的「第 N 阶段」 |

**收尾针对会话，刷新看板针对任何回合，换会话的判据看阶段与卡顿。** 下面说「每回合」就指一个回合，不要理解成一个会话。

## 一、会话开始：看 → 提 → 说 → 等

**先看档位**：单次档不用开工，直接干活；轻长期档默认也不喊口号，用户想看进度时才回三行；只有长跑档默认走这一套。

### 1. 看（有预算，别多读）

**读入集合，单会话单回合合计 ≤20 KB**：

| 读什么 | 读多少 |
|---|---|
| `.workbuddy/rules/工作空间规则.md` | **只读「〇、开工必读」** |
| `WORKBUDDY.md` | 全读（它很小）——重点看「本工作区必提醒」节 |
| `看板.html` | **只看「待办清单」「未了清单」「正在做」三块** |
| 记忆 | 只读 `MEMORY.md`；**日志不读** |
| `changelog.md`／素材登记 | **不读**（要用时 grep 定位） |

- 先 `git status`（没铺 git 的项目跳过）：有未提交改动 ＝ 有别的会话正在写 → **停手问用户**。
- **核一次基线**：拿看板里的基线，和产物标注的「依据 vX」对一遍。有产物落后，写进「风险」行。
- **核对看板有没有落后**：拿主线／要做的事／已定事项三块跟磁盘真实状态对一遍，**落后的当场补齐再报进度**——别只报「看板是旧的」。
- 轻长期档只有 `看板.html`，读它即可。

### 2. 提（先提，再说进度）

**提醒从哪来**：项目 `WORKBUDDY.md` → 「本工作区必提醒」节。这里放用户要求「以后每次都要提」的事。**该节不存在 ＝ 本项目没登记过长期提醒，别自己编一条。**

- 按该节每条写明的**触发点**（「新会话第一回合」「用户说开工」「阶段收口时」）逐条比，命中就提。
- **每处只提一次**——用户没接话就不追、不重复、不打断当前任务。
- **只提一句**，不写成任务列表，不在同一回合把同一件事提两遍。

### 3. 说（三行 ＋ 一行提醒）

```
进度  第 2 阶段 ｜ 做完 4/9 步 ｜ 正在做：生成第 1 讲课件
待办  等您回传素材
风险  演示页视频会随页序移动，重导后需重插
提醒  阶段收口了，要不要开次复盘会？（第 2 步命中时才有这一行）
```

- 步骤**说中文全名**，不要只说编号；有卡住的写清**在等什么**。
- 基线落差写在「风险」行，点出哪几件产物落后于哪一版。
- 需要用户拍板的单独列出。**正文不超过三行**（提醒单独一行，不计）。

### 4. 等

**用户没确认前不动手。** 不自动开始下一步，不一次抛多个问题。

## 二、会话结束

**先看档位，三档做的事不一样：**

| 档 | 收尾要做什么 |
|---|---|
| **单次** | **不用收尾**——做完直接把东西给用户 |
| **轻长期** | 产物 ＋ 看板 ＋ 核对 ＋ 清退 ＋ 报告（跳过下面表里的「存档」与「output 归类」） |
| **长跑** | 全做：下面的五件事 ＋ 报告格式（没铺 git 的项目跳过存档） |

**该做的当回合做完——没有「攒着做」。**

### 五件事

| 更新什么 | 怎么更新 |
|---|---|
| **产物** | 就地改**同一份文件**（一个产物一个文件） |
| **看板** | 五块：**主线**（只改状态，不改步骤）／**正在做**／**待办清单**（近期能收尾的）／**未了清单**（长期挂着的）／**已定事项**（只放仍生效的）。每块怎么写见 `assets/看板.html` 顶部说明；**什么时候该刷见下节**。写完不回读全文 |
| **存档** | 长跑档：`git add` **只加本回合动过的文件**（并行期间禁止 `git add -A`）→ 提交。**不 push**。轻长期跳过 |
| **output/ 归类** | `output/` 根上的**散件**移进对应任务文件夹（文件夹名＝客户端会话名，半角 `\|` 换全角 `｜`）。**只移动，不删** |
| **核对** | 逐条对照看板和磁盘：写了「完成」的，产物真的存在吗？不存在就改回真实状态并说明。**不许补一句话当产物** |

**清退废弃件走 `删除与归档.md`**，本文件不重说。

### git 三查（长跑档且已铺 git；**没铺 git 的直接跳过**）

1. **`git status --short` 必须干净**——不干净就逐条看是什么，别直接走人
2. **删过已入库的文件？** 同步 `git add -- <路径>` **把删除提交掉**。只从工作区删、不提交 ＝ 工作树永远脏
3. **动过临时文件？** 确认 `.workbuddy/tmp/` 已在 `.gitignore`（没有就补，并一起提交）

漏了第 3 条的后果：过程件会正常入库，`tmp` 清掉后 `git status` 冒出一大堆「已删除未提交」，`.git` 被撑大且工作树永远脏。

### output/ 归类

**`output/` 下每个任务文件夹名 ＝ 客户端会话名**（用户界面上看到的那个名字），**不自己另起简称**。

- 会话名带**半角竖线 `|`** 的，改用**全角 `｜`**——半角 `|` 在 Windows 文件名里非法。
- **会话名怎么查**：`~/.workbuddy/workbuddy.db` 的 `sessions` 表，按 `cwd` 过滤本项目、`custom_title` 优先、`title` 兜底。**只读打开**：

```python
import sqlite3, os
db = os.path.expanduser("~/.workbuddy/workbuddy.db")
c = sqlite3.connect("file:%s?mode=ro" % db.replace("\\", "/"), uri=True)
for sid, ct, ti, ca in c.execute(
    "SELECT id, custom_title, title, created_at FROM sessions "
    "WHERE cwd LIKE ? ORDER BY created_at", ("%<项目名关键字>%",)):
    print(ct or ti, sid)
```

- **散件怎么归**：`output/` 根上还有没进任务文件夹的文件 → 按上面查到的会话名移进去。**只移动，不删**；归属拿不准的留在原地并报给用户。
- 还剩几件没归，`scripts/体检.py` 的「output 顶层散件数」会报。

### 刷看板的触发点

**下面任一条出现就立刻刷，不等收尾、不等用户问：**

- 产物状态变了：完成／新增／作废／版本号变了
- 产生了新决定（用户拍板的，或双方确认的原则）
- 待办增删：新冒出来的、办结的、作废的

**只有「这一回合纯过程、上面三样一个没动」时才不刷。**

⚠️ **办结的当场划掉**——别留「已经做完还挂在待办里」。用户要看的是「还剩什么」，不是「干过什么」。
⚠️ **两个清单按短期／长期分**：待办清单 ＝ 这回合或近期能收尾的；未了清单 ＝ 可能挂几周、跨会话的。**两类优先级不是一回事，别混装一个块里。**
⚠️ **同一件事只在一处说**——看板是遗留的唯一出口，不在对话里另起一份零散清单。

## 三、日志归档三件套

当天记忆日志达到 **8 KB** 就归档一次（阈值来源见 `判据与阈值.md` §三）。它只增不减，不瘦身会让每回合都变重。

### 前置检查：这份日志是不是只有你在写

同一工作空间可能同时跑多个会话，共用同一份日志与看板。**动原文件前先看 mtime**：

```bash
ls -la --time-style=+%H:%M:%S .workbuddy/memory/YYYY-MM-DD.md
```

- **几分钟内被写过**（且 `git log` 里有不是本会话的提交；没铺 git 的改看 mtime ＋ 旁证文件）→ **只做「全文存档」，不替换原文件**。替换会把它刚写或正在写的内容冲掉。
- 旁证不止 mtime：`git status` 里出现**本会话没动过的文件** ＝ 并行会话在活动。
- 处置：把「日志超标、未精简、原因＝并行会话」一句话报给用户，**等他定**（只有他知道有几个会话在跑）。
- **全文存档本身无风险，任何时候都做。**

### 三件（缺一不可）

| # | 做什么 | 规范 |
|---|---|---|
| 1 | **全文存档** | 复制到 `archive/专题-日志归档-YYYYMMDD/memory-YYYY-MM-DD-全文.md`，**一字不改**；**先 `diff` 校验字节一致，再动原文件** |
| 2 | **原文件换精简版** | 抬头**必须写三行**：① 全文在哪（路径＋字节数）② **怎么查**：「不要整份读，用 Grep 按关键词定位行号，再 Read 前后 20 行」③ 长期结论已升进 `MEMORY.md`。正文只留**当天要点表** ＋ 待续 |
| 3 | **结论升级** | 可复用结论（口径／约定／反复踩的坑）搬进 `MEMORY.md`。**日志只留流水，结论不留在日志里** |

抬头那三行是给下一个助手看的：一打开就知道「别整份读、去哪查、结论在哪」。**没有这三行，归档等于埋了。**

## 四、报告格式

一张分区小表，不是五行文字：

| 栏 | 写什么 |
|---|---|
| **做了** | 一句话结论 |
| **改了** | 改前 → 改后（成对列） |
| **影响** | 影响谁、影响哪几件产物 |
| **遗留** | 还没动的、待用户拍板的 |
| **下一步** | 「这回合该换会话了」——长跑档一个会话跑满 10 回合即结束（判据见 `判据与阈值.md` §八），开新会话说「开工」接着做 |

**不复述「我更新了哪几个文件」。** 给用户看的东西优先出 HTML 或表格，禁止大段文字。

## 五、禁止

**开工侧**

- 不产出业务成品。
- 不自己把「等验收」改成「已完成」。
- 不重排步骤编号。
- **不整份读累积型文件**（记忆日志）。
- **不把提醒变成自动执行**——「要不要开复盘会」是问，不是开。

**收尾侧**

- 不把没做的事写成做完。
- 不自己给自己发合格证（「等验收」→「已完成」只能用户改）。
- 不改验收标准（要先问用户）。
- **不每回合全量刷所有文件**——信息会被淹没，用户也读不出重点。
- **不手写改动明细**（那是 git 的活）。
