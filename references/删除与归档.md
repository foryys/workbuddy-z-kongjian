# 删除与归档

**`rm -rf` 是真删，禁用。** 任何删除都走这一份流程，不许在别处另起一套。

## 一、只有一条通道

Windows 上把文件／目录送进回收站，可用的写法只有一种——PowerShell 直接引用 .NET 类型：

```powershell
# 删文件
[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteFile('C:\path\a.md','OnlyErrorDialogs','SendToRecycleBin')

# 删目录（含全部内容）
[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteDirectory('C:\path\dir','OnlyErrorDialogs','SendToRecycleBin')
```

**三个前提，缺一不可：**

1. **不加 `Add-Type -AssemblyName Microsoft.VisualBasic`**。加了必被本机安全策略拦（禁止运行时编译 .NET 代码）；该类型无需它即可直接引用。
2. **走 WorkBuddy 的 PowerShell 工具通道**。从 Bash 或 Python `subprocess` 调 `powershell.exe` 会被拦（报 `TypeNotFound`，换 `-EncodedCommand` 也一样）。
3. **用前先确认回收站没满**。满了以后新删文件**不进站、直接永久删除**，而且不报错——看着像通道被拦死，其实是站满了。先清空或腾出空间再删。

**两条走不通的路，不要试**：`ctypes` 直调 `SHFileOperationW`（结构体传参有坑，返回 `rc=2`）／`New-Object -ComObject Shell.Application`（COM 实例化被拦）／pythonnet 的 `import clr`（无此模块）。

## 二、判成败只看结果

**不看命令返回，不看 `try/catch`。**

- `catch` 全部命中，**不代表删除失败**——可能只是反射取类型那一步触发，循环删除实际全部成功。
- `catch` 没报错，**也不代表删除成功**——照样得回读目录。
- 删目录会抛「这个系统不支持该功能」或「系统调用级别不正确」，**内容很可能已经进站**；报错后目标目录还在，多为**只剩空壳**。别被报错骗回去重做。

**三个核对，全过才算删掉：**

| # | 核对什么 | 通过标准 |
|---|---|---|
| 1 | 源路径 | 已空或不存在（删目录时只剩空壳也算内容已清） |
| 2 | 回收站 | 按原始路径查得到对应 `$I`／`$R` 成对条目 |
| 3 | 字节量 | 回收 ≥ 删除前，即无丢失 |

只满足第 1 条时必须**另留一份可回滚副本**，并在汇报里说清「已清、原件在某处」。

**残留空壳怎么清**：再走一次回收站调用，或 `rmdir`（仅删空目录）。⛔ **绝不在回收站调用后面写 `Remove-Item -Recurse` 兜底**——一旦真没进站，它就是绕过回收站硬删了。

**验证从 Bash 侧做**：本机 PowerShell 工具不回显 stdout，删除是否成功用 `ls`／`find`／目录计数复核，不靠脚本自己打印。

**怎么按原路径查回收站**：看 `$I` 元数据文件。头是 `<qqqI`，**原始路径在偏移 28**（按 UTF-16LE 解；用偏移 24 解出来全是乱码），`$I` 字节数除以 2 减 20 即路径字符数。`$I` 的 mtime ＝ 删除时刻，按「最近 N 分钟」筛一遍最省事。删 D 盘的东西，`$I` 在 `D://$Recycle.Bin//<SID>`，不在 C 盘。

## 三、分级收口

**不许一发现没用就直接删。** 三步：

1. 收尾时把本轮无用件**移进暂存区** `archive/待回收-<范围>-YYYYMMDD/`（**只移动，不销毁**）
2. **一句话**告诉用户归档到哪个文件夹——不解释过程
3. 到回收点时出清单 → 用户点头 → 送回收站

**回收点哪一级收口就在哪一级清：**

| 层级 | 什么时候 | 清什么 |
|---|---|---|
| **任务级** | 单次任务做完 | 该任务的过程件 → 进暂存区 |
| **支线级** | 一条支线收口 | 该支线全部暂存区 → 送回收站 |
| **项目级** | 整个项目结束 | 所有暂存区 → 送回收站 |

**判据：更上一级已完工 → 说明下级的东西不会再动，可以真删。**

不把回收点只设在「项目结束」的理由：那个时点可能一年后才到，而助手只在会话里存在——等不到的回收点等于没有回收点。

不边做边删的理由：「这东西还有用吗」当场最容易判错。暂存区把判断推迟到信息最全的收口，中途随时捞得回来。

**回收站不是备份**——助手无法可靠地从回收站取回文件，真丢了只能用户手动还原。

## 四、清空重做（「只留 XX」）

**这是唯一允许「大批量清」的场景，也是最容易出事的场景。四个动作按顺序，一步不能跳。**

1. **出两份清单**：「保留」与「删除」各列一份，逐条写路径与大小。**不要只出删除清单**——用户需要对照着看才知道要保的是什么。
2. **逐条点头**：一份清单点一次不够，**按条目确认**。用户只说了「只留 XX」不等于授权删其余全部。
3. **整目录备份**：动之前先把整个目录复制一份**到要清的目录之外**，目录名带日期。**并验证备份可读**（能列出文件数）。备份没验过等于没备份。
4. **分批走回收站**：不一次清完。每批做完**回读目录复核**再走下一批，中途发现不对就停——此时备份还在。

**全程禁用 `rm -rf`。** 走回收站的写法和验收标准见本文件前两节。

**只清几件时不要走这套** —— 走第三节的分级收口就够了。清空重做是「整目录作废重来」级别的动作，杀鸡用牛刀反而增加误删风险。

## 五、归档

**归档件不参与去留判断的争论，只守三条：**

1. **独立命名，禁止同名覆盖**。一律 `<类型>-<说明>-YYYYMMDD[HHMM].md`。确需覆盖的先验「新 ⊇ 旧」，拿不准就换带时间戳的新名。
2. **只移动不销毁**。走上面的回收站流程，先出清单、文件名逐字核对（写错一字会被静默跳过）、删完回读目录。
3. **同一产物快照只留最近 3 份**。不「每轮一份」。

**批量删除前逐字核对文件名**，删除后必须回读目录复核。文件名写错一个字符，`Test-Path` 即为 false、被静默跳过，命令却报成功。

## 六、git 里的删除

删掉已入库的文件，**必须同步提交删除**：

```
git add -- <路径>
```

只从工作区删、不提交，工作树永远脏，那份「已删除未提交」会一直挂着。

**动过临时文件就先确认 `.workbuddy/tmp/` 在 `.gitignore` 里**，没有就补上并一起提交。漏了会让过程件正常入库，`tmp` 清掉后 `git status` 冒出一大堆「已删除未提交」。

删除类操作一律先出清单、让用户点头；文件名逐字核对；删完回读目录复核。
